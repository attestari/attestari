Plate I

The whole map

Attestari is one engine behind six entry points. Every write becomes an event on an append-only log, every read comes from a projection rebuilt out of that log, and the proofs hang off the same log.

Three ideas carry the whole design

  • The log is the database. Six immutable event types are the source of truth. The knowledge graph, the vectors and the keyword index are projections that can be dropped and rebuilt (plate III).
  • Every guarantee lives in shared code. All three storage tiers extend the chain with the same audit.next_entry() and manage keys through the same KeyManager, so the audit chain and the shred cannot drift between in-memory, SQLite and Postgres (plate VIII).
  • Ports keep the core dependency-free. Extractor, Embedder, EventStore and ProjectionBackend are Python Protocols. The defaults use only the standard library; Claude, sentence-transformers and Postgres plug in behind the same shapes (plate XIV).

Plate II

The write path

One add() call records the raw message as an episode, extracts triples, skips what is already known, closes the old value of a single-valued predicate, and asserts the rest. Every append also extends the audit chain, and seals personal data when a KEK is set.

The rules add() applies

RuleWhat the code does
Episode firstEpisodeIngested with content_hash = sha256(text) is appended before extraction runs. With a KEK, the store replaces that hash with a keyed k1: HMAC under the subject's commitment key (0.0.7).
DedupA (subject, predicate, object) triple that is already live, or repeated within the same message, is skipped. No event is written.
SupersedeFor a single-valued predicate, a different value closes the live fact with FactInvalidated(reason="superseded", valid_to=<new valid_from>). The old row stays, and superseded_by names the new fact (0.0.7).
CoexistMulti-valued predicates only add: uses, speaks_language, likes, knows, owns, visited, interested_in, member_of. Any predicate not in that set is treated as single-valued.
Timevalid_from defaults to now in UTC; strings go through datetime.fromisoformat; naive datetimes are read as UTC. recorded_at is always the moment of the call.
Idsuuid4 strings in canonical form, so Postgres UUID columns round-trip byte for byte and audit digests re-derive exactly.
After the loopbackend.on_write(): a no-op for the in-memory fold, a full rebuild of edge and entity on Postgres, in one transaction under the event-log lock (0.0.7).

The two extractors

DeterministicExtractor · zero dependencies

Four regex rules for first-person sentences, with the object required to start with a capital letter:

  • name_is: my name is, I am, I'm
  • lives_in: I live in, I now live in, I moved to, I relocated to
  • works_at: I work at, I work for, I joined, I now work at
  • uses: I use, I switched to, I now use, I prefer

Confidence 1.0, exact character span. Drives the tests, CI and every demo. "I have a dog" yields nothing.

AnthropicExtractor · production path

Claude structured output through messages.parse with a schema of subject, predicate, object and confidence. First-person statements are attributed to the subject id. Default model claude-opus-4-8, overridable with ATTESTARI_EXTRACTOR_MODEL.

Retries 408, 409, 429, 5xx and dropped connections with exponential backoff (2 s doubling to 60 s, honours retry-after, up to 8 retries). The span is the first text.find(object). default_extractor() picks Claude when ANTHROPIC_API_KEY is set and the SDK is installed; the REST and MCP servers use it, bare Memory() stays deterministic.

Plate IV

Two kinds of time

Each fact carries a valid-time window, when it was true in the world, and a system time, when Attestari recorded it. Corrections close windows instead of deleting rows, so a search can replay any date.

A query with as_of answers "what was true on that day". It does not answer "what did the system believe on that day": the system-time columns are stored, but no query reads them yet. The 15 Jan 2026 preset shows a day where the two answers differ.
Plate V
The read path
search() filters first and scores second. Only facts valid at the requested instant, for the requested subject, become candidates. Each is scored on two channels, and the weights depend on whether the embedder carries real meaning.
A worked example, from a real run
query   "where does the user live"     tokens: doe · live · the · user · where
fact    "alice lives_in Berlin"        tokens: alice · berlin · in · live

keyword   1 shared (live) ÷ 5 query tokens   = 0.200
semantic  cosine of the two hash vectors          = 0.224
score     0.4 × 0.224 + 0.6 × 0.200            = 0.209   (hash-embedder weights)

Plate VI
The audit chain
Every append adds an entry whose hash covers the previous entry and a digest of the event. The chain-only check catches reordering, insertion and deletion. The deep check also re-derives each event's digest and catches silent edits. Both accept a sanctioned crypto-shred and flag a rogue key deletion.

From 0.0.7, when a KEK is set and the event has a subject, content_hash and object_hash are keyed commitments: a k1: HMAC under a key derived from the subject's DEK. Shredding the DEK destroys that key, so a retained hash can't confirm a guessed value. Deep verification re-derives them with the keys of the subjects that are still live. Without a KEK both stay plain sha256, and entries written by 0.0.6 or earlier keep theirs.
entry_hash = sha256(prev_hash + payload_hash), and the first prev hash is 64 zeros. Timestamps are committed as epoch microseconds so a Postgres round-trip re-derives byte for byte. Deep verification walks entries against readable events and skips an entry only when its ref is in erased_refs(): the subject's key is gone and a tombstone exists. The default check needs no event content at all, which is what lets it vouch for a shredded log.
A full rewrite of the whole chain is internally consistent. Detecting that requires recording the head hash somewhere the operator cannot rewrite; Attestari prints it, publishing it is a manual step today.
Plate VII
Crypto-shred and forget
Each subject's payloads and fact objects are sealed with that subject's own data key, and one root key wraps every data key. forget() deletes the wrapped data key, so every copy of that ciphertext, in backups and replicas included, goes dark at once, while the audit chain and a signed certificate remain.

How an append stays atomic
  • SQLite: the event row, its audit row and a freshly minted data key commit in one BEGIN IMMEDIATE transaction, so a crash cannot leave the chain out of step with the log. Each event row's seq equals its audit entry's seq.
  • Postgres: one transaction per append takes an advisory lock, reads the last entry hash, inserts the event row with event_seq and the audit row. From 0.0.7 the event is sealed inside that transaction (ciphertext plus keyed hashes), and a lock keeps threads that share one connection from mixing their transactions. events() merges episode and fact_event back into one order by event_seq.
  • Postgres projections: rebuild() truncates entity and edge and re-inserts every row after each write. From 0.0.7 it runs as one transaction under the same advisory lock as appends, so rebuilds from several workers queue instead of colliding, and a search waits for the new table rather than reading a half-built one. It is still O(n) per write; incremental projection is the next step (plate XV).

Plate X
Governing Mem0 and Zep
wrap() leaves retrieval with the store you already run. It records every write in Attestari's chain before passing it on, passes searches straight through, and turns the downstream delete into evidence by reading the subject back.
from attestari import Memory
from attestari.wrap import wrap

governed = wrap(mem0_client, ledger=Memory.postgres())   # adapter inferred from the client's module
governed.add("I live in Berlin.", subject_id="u1")        # ledger first, then Mem0
governed.search("where do I live", subject_id="u1")       # straight to Mem0
receipt = governed.forget("u1")
receipt.complete, receipt.downstream_verified, receipt.downstream_error, receipt.certificate

Calls made through attribute passthrough on the wrapped client are not recorded; only add, search and forget are governed. Attestari cannot shred data inside someone else's service, because it does not hold their keys. A wrapped deployment proves that the deletion was requested, that the downstream delete was called and what it returned, that Attestari's own copy is unrecoverable, and that none of that was altered afterwards.
Plate XI
Using it as a memory layer
Every integration runs the same loop: add the user's words after they speak, search before the model answers, put facts and their ids into the prompt, and forget on request.
Five ways to wire it
1 · In-process Python
One agent process, or a service with its own Postgres.
from attestari import Memory

mem = Memory.local()          # Memory.postgres() for a shared service

def remember(user_id, text, msg_id):
    mem.add(text, subject_id=user_id, source_ref=f"chat:{msg_id}")

def recall(user_id, query, min_score):   # tune min_score on your own data
    hits = mem.search(query, subject_id=user_id, limit=5)
    return [f"{h.edge.predicate} {h.edge.object} [fact {h.edge.fact_id[:8]}]"
            for h in hits if h.score >= min_score]

The host spawns the server; memory lands in the SQLite file and survives restarts.

Rules that keep it honest in production
  • Use an opaque, pseudonymous subject_id. It stays in plaintext after a shred.
  • Pass source_ref (message id, document id) on every add; it is the receipt that get_provenance returns. Keep personal data out of it for the same reason.
  • Backdate with valid_from when a message reports a past change ("I moved in March").
  • Threshold search() scores instead of trusting answer(); it returns the top object even for an unrelated question.
  • Declare multi-valued predicates your extractor produces, with PredicateRegistry.declare, or Claude's free-form predicates will supersede each other.
  • Serialise writes per subject. Supersession is a read-then-write without a lock.
  • Preview every erasure with dry_run, pass the preview's manifest_hash as expected_manifest so the erasure covers exactly what you reviewed (0.0.7), and keep the certificate the real call returns.

Health and patient assistants
An intake or follow-up assistant remembers symptoms, medications and preferences across visits.
Patients can ask for erasure, and clinicians ask why the assistant believed something. Provenance answers the second; crypto-shred and the certificate answer the first.
Set up: Pseudonymous patient key as subject_id; message or document id as source_ref; KEK held in a KMS.
Watch: The shred covers the memory layer only, not the record system, application logs or model providers. From 0.0.7 the hashes a shred leaves are keyed; entries written by 0.0.6 or earlier can still confirm short, guessable values (plate XV).
Banking and fintech copilots
A relationship-manager copilot or collections agent remembers circumstances and commitments.
Disputes ask what the assistant knew when it recommended something: as_of plus provenance plus a tamper-evident history.
Set up: valid_from on every reported change; deep verify on a schedule; head hash recorded outside.
Watch: Retention law can require keeping some records. Gate forget() behind your retention policy and preview with dry_run.
Insurance claims and underwriting
A claims agent extracts facts from claimant messages and adjuster notes.
Each fact links to its source document, and as_of reconstructs the file on the decision date. Life and health insurance pricing is listed as high-risk in the AI Act (Annex III).
Set up: source_ref = claim document id; one subject per claimant.
Watch: as_of slices valid time; reconstructing what the system knew on a date needs a system-time query (plate IV).
HR and recruiting assistants
A screening assistant keeps candidate facts across interview rounds.
Rejected candidates ask for erasure, and employment uses are high-risk under the AI Act (Annex III), so record-keeping matters.
Set up: One subject per candidate; interviewer notes ingested with the candidate's subject_id.
Watch: forget() is scope-based. Notes about a candidate stored under an interviewer's subject_id survive the candidate's erasure.
Support bots with customer memory
A support agent remembers a customer's plan, devices and past issues.
Erasure requests arrive in volume. Each gets a certificate, a verify --user check and an evidence bundle for the DPO.
Set up: wrap() if memory already lives in Mem0 or Zep; otherwise Postgres behind the REST server.
Watch: With wrap(), Attestari proves the downstream delete was called and read back; it cannot shred inside the vendor.
Tutoring and education
A tutor remembers a learner's level, goals and accommodations.
Learners or guardians request deletion, and education uses are high-risk under the AI Act (Annex III).
Set up: Postgres for a school platform; Memory.local() for a single-learner app.
Watch: Declare multi-valued predicates such as studies or struggles_with, or new values will close old ones.
Legal and compliance copilots
Matter-scoped memory for a legal assistant.
Provenance to the exact source passage, a history nobody can quietly edit, and as_of for what was known at filing.
Set up: subject_id per matter or client; source_ref = document id and page.
Watch: Entity merges are recorded but reads do not follow aliases yet (plate XV).
Personal assistants over MCP
A person runs attestari-mcp beside Claude Desktop; memory lives in one local file.
User-owned, durable memory with provable forget and no infrastructure.
Set up: Set ATTESTARI_KEK so forget is cryptographic and certificates are signed.
Watch: SQLite reads scan the whole log (about 100 ms at 12k events). Leave forget_subject off, the 0.0.7 default, unless the agent is meant to erase people.
Multi-agent internal platforms
Several agents share memory about customers or projects.
Per-fact provenance, agent_id recorded on every episode, one audit chain across agents.
Set up: Encode tenancy in subject_id, or run one deployment per tenant.
Watch: Reads filter only by subject_id; agent, session and org scopes are recorded but not enforced at query time.
Teams already on Mem0 or Zep
Keep your retrieval stack and add the audit trail and deletion evidence.
No migration: wrap(client) in Python, or ATTESTARI_WRAP_UPSTREAM in front of an HTTP service.
Set up: A durable ledger (Postgres for a shared service); read-back configured so receipts can say verified.
Watch: Searches pass through untouched, so Attestari's provenance and time travel apply to its own ledger, not to the vendor's answers.
Poor fits today
  • Chasing retrieval leaderboards. The internal LOCOMO evidence-recall proxy is 0.711 with MiniLM embeddings and 0.661 with the hash embedder; the project does not compete on that axis.
  • Multi-hop graph reasoning. Retrieval has a semantic and a keyword channel and no graph traversal.
  • High write rates on one Postgres. Every write rebuilds both projection tables.
  • Erasing every mention of a person across other people's memories. forget() removes one subject's scope.
  • Policies that require physical overwriting of media. Crypto-shred destroys keys, not bytes.
  • Query-time tenant isolation by org or agent. Only subject_id filters reads.

Plate XV
Sharp edges
What the code does that a deployer should know before relying on it. Surveyed against 0.0.6 on 4 October 2026 and revised for 0.0.7 on 9 October 2026: ten items are still open, six of them now stated in the docs, and five are fixed.
Still open in 0.0.7
privacy
Only payload and object are sealed
Documented in 0.0.7
subject, predicate, scope ids, source_ref, timestamps and char_span stay readable in the log after a shred. With Claude extraction, subject can be a third party's name.
Evidence: Read from store.py, store_sqlite.py and store_postgres.py.
Direction: Use opaque subject ids and keep personal data out of source_ref; the README and the GDPR Article 17 page say this from 0.0.7. Sealing these fields too is the code fix.
behaviour
forget() is scope-based, not mention-based
Documented in 0.0.7
A fact about alice extracted from bob's message lives in bob's scope and survives forget("alice").
Evidence: Reproduced: after the forget, timeline() still held alice lives_in Paris with scope bob.
Direction: The erasure docs now say so. A mention index would let an erasure reach facts in other subjects' scopes.
behaviour
Two concurrent add() calls break single-valued supersession
Documented in 0.0.7
add() reads the live projection, then appends. Two writers for one subject both see the old value and both assert a new one. The 0.0.7 Postgres fix makes concurrent writes safe for the log and the projection tables, not for this check.
Evidence: Reproduced with two threads and a 200 ms extractor: Berlin and Paris were both live for lives_in.
Direction: Serialise writes per subject in the caller, as the README's deploy checklist now says. In the engine, re-check the live value inside the append lock.
behaviour
Unknown predicates are single-valued
Claude produces free-form predicates. has_pet Rex followed by has_pet Mia closed Rex.
Evidence: Reproduced with a fixed extractor.
Direction: Declare multi-valued predicates, have the extractor return cardinality, or default unknown predicates to multi. Score the change on the cached LOCOMO run first.
behaviour
answer() has no relevance floor
"What is the user's favourite colour" returned "Alice" with score 0.147, because answer() returns the top object whatever its score.
Evidence: Reproduced on the in-memory tier.
Direction: Threshold search() scores in the caller; an optional min_score on answer() would make the safe path the easy one. Hash and semantic scores need different thresholds.
behaviour
Entity merges do not change reads
Documented in 0.0.7
Merges and unmerges are recorded and reversible, but search, timeline and answer never consult alias_of.
Evidence: Reproduced: after merging "the founder" into u1, timeline(subject="the founder") returned nothing.
Direction: The README and ARCHITECTURE now say reads don't follow merges yet. Resolving aliases during the fold is the code fix.
behaviour
as_of slices valid time only
Documented in 0.0.7
tx_from and tx_to are stored and break ties, but there is no "what did it believe at system time T" query, which is the question an audit or dispute usually asks.
Evidence: Read from projection.py and retrieve.py; plate IV shows a day where the answers differ.
Direction: The comparison tables now ask "what was true on date D?", and the docs say system time isn't queryable yet. An as_of_system parameter that filters on recorded_at and the invalidation's recorded_at would add it.
scale
Whole-log reads, and a full rebuild on every write
The in-memory and SQLite tiers fold the entire log on every read and write. On Postgres, search is indexed, but add(), timeline, provenance and conflicts fold the log, and every write rebuilds both projection tables.
Evidence: SQLite search p95 was 98 ms at 12,003 events, about twice that with a KEK. On Postgres, add() took a median of 730 ms at about 600 facts on 0.0.6; batched inserts bring that to 367 ms in 0.0.7, and it still grows with the log.
Direction: Snapshots and incremental projection, both already named in ARCHITECTURE.md. On Postgres this should land before real traffic.
operations
The REST server has no authentication
Anyone who can reach the port can read, write and erase. The README's deploy checklist says to put your own auth in front.
Evidence: Read from server.py.
Direction: An optional bearer token with POST /v1/forget behind it. Until then, keep the server on localhost or a private network.
operations
Certificates persist only on Postgres
Documented in 0.0.7
The in-memory and SQLite tiers hand the certificate back once from forget(). The evidence bundle reports certificates: null for them.
Evidence: Read from evidence.py and backend.py.
Direction: Store the returned certificate yourself on those tiers, as the README now says. A SQLite certificate table would close it.
Fixed in 0.0.7
security
Retained hashes confirmed guessed values after a shred
Fixed in 0.0.7
Up to 0.0.6, an encrypted episode was committed as an unkeyed sha256 of its text, and a fact's value as an unkeyed sha256 inside an audit digest whose other fields stay readable. After forget("alice") with a KEK, recomputing that digest for six candidate cities confirmed "Berlin", and the sha256 of a guessed sentence matched the episode's content_hash.
Fix: With a KEK, both are now HMACs (k1:) under a per-subject key derived from the subject's DEK, so shredding the DEK destroys that key too. The same attack on 0.0.7 confirms nothing, and deep verification still passes.
Evidence: Reproduced on 0.0.6 and re-run on 0.0.7 on 9 October. tests/test_keyed_commitments.py runs the attack on the in-memory and SQLite tiers and verifies a log written by 0.0.6.
Still true: Entries written by 0.0.6 or earlier keep their unkeyed hashes, because rewriting them would break the chain. A fact's span still reveals the length of its value.
concurrency
Postgres broke under concurrent writes
Fixed in 0.0.7
Listed from code reading on 4 October and reproduced on 9 October. With uvicorn --workers 4, 44 of 60 add() calls raised although all 60 had been saved, and 39% of searches for an existing fact came back empty. Four threads sharing one engine failed every write, because psycopg doesn't isolate transaction blocks between threads.
Fix: rebuild() runs as one transaction under the event-log lock, a lock guards the shared connection, and a shred commits together with its certificate. The same reproduction raised nothing and returned no empty searches.
Evidence: Two regression tests in tests/test_postgres.py, both failing on 0.0.6.
operations
The MCP server could erase a subject in one call
Fixed in 0.0.7
forget_subject erased on a single tool call with no dry run at the server, so a prompt injection could request an irreversible erasure.
Fix: The tool is offered only with ATTESTARI_MCP_ALLOW_FORGET=1, is flagged destructive, and takes two calls: a preview that returns the manifest hash, then a confirmation that passes it back and is refused if the subject's records changed. Memory.forget(expected_manifest=...) does that check.
Evidence: tests/test_mcp.py and tests/test_spike.py.
docs vs code
Retrieval has two channels, not three
Docs corrected in 0.0.7
README and ARCHITECTURE described semantic, keyword and graph retrieval. retrieve.py and the Postgres SQL implement semantic and keyword only.
Fix: The docs now describe two channels and say graph expansion isn't implemented.
minor
Small drift
Fixed in 0.0.7
add() never filled FactInvalidated.superseded_by, and the README badge said 122 tests.
Fix: add() records the superseding fact's id, and the badge reads 138, the count that passes with Postgres.
